# 子 agent 委托经验（写稿 / composition 前必读）

## 第一部分：旁白口语化清单

目标：让旁白像**有经验的讲解员在镜头前说话**，而不是产品文档、PPT 备注或标签罗列。下面每条都是实际返工过的病症，写稿时逐条对照。

## 1. 五类必改病症

### 1.1 单字动词（歧义）

- 「挂 CI」：挂＝崩溃／挂载／接入，观众会理解反。写「接进 CI 流水线」。
- 「调 agent」：调＝调用／调试／调参。写「在本地被 agent 调用」。
- 「出评论」：谁出？写「每处修改都会给出带行号的评论」。
- 同类：跑→执行、改→改成、看→查看、传→交给。

### 1.2 生造复合词

「审核台」「知识包」这类词在观众脑中不存在。用动作和场景替代：先说 agent 交计划，再说浏览器弹出网页，再说你划线批注。**不要**给产品起新名字。

### 1.3 分类说明句

「这是给 agent 用的」「专门给人用」「为 X 设计」——这是给写稿人的分类备注，不是内容。观众不关心归类，关心「我遇到什么、它怎么接住」。

### 1.4 电报体（无主语 / 名词堆叠）

- 反例：「写卡片漏自适应，给 container queries。」
- 反例：「改双语漏同步，把 message_en 与 message_zh 打包同审。」
- 正例：「很多人把卡片塞进窄侧栏，agent 只看屏幕宽就挤变形。指南会让它加 container queries 按容器重排。」

每句自检三要素：**谁 — 做什么 — 结果是什么**。缺一个就重写。

### 1.5 主语模板化

治了「缺主语」之后很容易变成句句「你……」。硬性上限：**同一主语开头的段落不超过全片 40%**，连续两句不得同一种开头。

可用开头轮换：你 / agent / 它 / 很多人 / 最常见的情况是 / 时间状语（「提交大 PR 时」）/ 直接陈述动作（「装上技能后，弹窗会改成原生 dialog」）。

## 2. 术语处理

- 首次出现带解释性同位语：CI 流水线、review unit（审查单元）、hook（钩子）、MCP 的上下文窗口。
- 第二次起可以简称。
- 行业黑话换日常说法：口播→录好的说话视频；裸写命令→自己手写命令；烧 token→把上下文塞满、花更多钱。

## 3. 句子长度与连接

- 单句 15–35 字，允许一句两个短分句。
- 允许口语连接词：「这时候」「结果」「所以」「你可以」「问题在于」「更麻烦的是」。
- 禁止把三句压成一句用分号串起来。

## 4. 念出来自测

写完把每段读一遍（或默读出声）：

1. 这像不像一个人在跟你讲？像 PPT 备注就重写。
2. 有没有需要听众猜的缩写或动词？有就展开。
3. 连续两句是不是同一个开头？是就换。
4. 有没有「更高效、更可控、补齐规范」这类评价？删掉，换成具体动作或数字。

## 5. 与字数的关系

口语化会变长。**先保证每场讲清楚，再压字数**；宁可延长时长（3–5 分钟区间内），也不要把句子压成标签。压字数优先删评价句、重复句和形容词，不删主语和动词。

## 6. 提交前机械检查

- 搜一遍单字动词：`挂`、`调`、`出`、`跑`、`改`（作动词时）。
- 搜「给人用」「给 agent 用」「专门为」。
- 统计以「你」开头的段落占比。
- 统计非空白字符数是否落在目标区间。

## 第二部分：composition 流程教训

### 2.1 先写 storyboard，再写代码（硬顺序）

**教训来源**：2026-11-22 GitHub 周榜视频，子 agent 在 scene-config.json 生成后直接跳进写组件和 29 个场景代码，跳过了 storyboard.md；主 agent 续跑指令里明确把 storyboard 列为第 2 步，模型仍未执行，一路写到 check/渲染阶段才被发现。此时补写的 storyboard 只能是「先射箭后画靶」的反向记录，失去了它最重要的作用——**在写码前暴露设计问题**。

**规则**：

1. 顺序锁定：scene-config.json → **storyboard.md（写完即停，等确认）** → 逐场景代码 → check → 渲染。storyboard 没写之前，禁止创建任何 compositions/ 下的场景文件。
2. 给子 agent 的指令里把 storyboard 单独列为一个带完成标准的步骤（「写完后列出每场景的 template/layout/素材 id，确认无误再进下一步」），不要把它和后续步骤合并成一段，否则模型倾向跳过文档直接写码。
3. 不要把「scene-config.json 已存在」当成 storyboard 已完成的理由。scene-config 是时间/布局的机器可读数据；storyboard 是给人审的设计文档（为什么这个布局、素材怎么演绎、动画怎么设计），两者缺一不可。
4. 事后反向补写的 storyboard 必须逐条和真实代码核对一致，并在文件开头注明「事后补录」及原因；不能拿它和代码互相矛盾的地方糊弄 gate 校验。

### 2.2 Phase 8 gate 必须双检查器：stock 检查器 + 密集布局审计

**教训来源**：2026-11-22 GitHub 周榜视频，两轮审片都栽在同一件事上——`check-composition.py` 报 0 findings，但用户肉眼看到多处文字溢出。根因有两个：(1) 它每场景只采首/中/尾 3 个时间点，cue 到达瞬间的溢出采不到；(2) SVG `<text>` 没有 scroll/client 尺寸，「文字画出卡片/底板」它天然测不到——唯一的 svg_text_overflow 规则要求 `<g>` 恰好含 1 个 rect 才能配对，代码行高亮组（group bbox 只有首行高亮条 32px 高）和 IDE 面板行号列（bbox 不含 gutter）全是假阳性或漏检。

**规则**：

1. Phase 8 验收 gate 改成双过才算 pass：`check-composition.py`（stock）+ `scripts/dense-layout-audit.py`（8 采样点/场景）。
2. dense-layout-audit 的 `html_clip` 和 `panel_escape` 是真实溢出判据（发现即退出码 1）；`beyond_group` 已知有大量结构性假阳性（行高亮组/行号列/gutter 对齐），只作线索，必须结合代码坐标人工复核；`long_lines` 是风险候选。
3. 带大量英文/代码行的场景，优先用 IDE/terminal 大面板做容器（顶栏三圆点+文件名标签、行号列、深色底、面板占 main 区 70%+），代码文字 20-22px 等宽细体（weight 400-500）并标 `data-text-role=ui`（检查器 UI 字号下限放宽到 20px：`--min-ui-font-size 20`）；大面板让「文字有没有出头」既肉眼可核、又可被 panel_escape 规则自动判定。裸 `<text>` 代码行是溢出重灾区，禁止在窄卡片里堆代码。
4. 字幕/旁白时间轴变化后，index.html 里所有挂载点（场景 div 的 data-start/duration + chrome 组件）要同步改，漏一处就会报 scene_mount_missing / presenter not visible；零时长字幕单元会让 caption-bar 的末行 GSAP 状态机错乱（文字常显），必须给个真实窗口。

## 第三部分：本期复盘问答（2026-11-22 GitHub 周榜视频）

本期流程：research → script → voice-clone 旁白 → 素材 harvest → scene-plan → composition（29 场景）→ 布局审计四轮 → 渲染 → 成片 QA → BGM 混音 → 三尺寸封面。四轮用户审片分别驱动：去 zoom / 开场重设计 / 溢出修复 / IDE 面板范式改造。

### 3.1 zoom-in to focal region 什么时候用合适

本期正反例都有。**适用**：大图里 focal 目标很小、旁白点名某个细节时做一次性强调——单张图表的某根线、报错截图的错误行、架构图的某个模块。要点：整段只推一次，scale ≤1.4–1.6、时长 ≥1.2s、起止都停稳；推近后非焦点区域顺手压暗，观众视线有着落。**不适用**（本期被用户打回的用法）：清单巡讲类场景（s02 逐个解释排行榜项目）——观众需要持续看到完整榜单上下文，README 跟着 cue 逐个 zoom-in 会晕、且榜单一出画就丢了叙事锚点。这类场景保持匀速慢滚 + 切换停 1s 即可。判断口诀：**zoom 是给「看一眼这个细节」用的，不是给「逐个条目巡讲」用的。**

### 3.2 为什么过滤掉大量图片/视频素材（ffmpeg-skill 主页明明有很多图和视频）

过滤不是稀缺而是**适配**，四条规则叠加后剩下的自然不多：
1. **贴 beat**：素材必须落在旁白当前那句的时间窗里，讲 probe→verify 四步保护时用 demo 视频，讲 star 数时用榜单截图；主页 20 张图里真正对得上那一刻的只有 1–2 张。
2. **素材不连续复用**：同一来源隔 ≥2 场景才能再出现，ffmpeg-skill 的演示视频和截图不能连场堆。
3. **清晰度门槛**：网页上的小 GIF/缩略图（宽 400–600px）铺满 1080p 区域必发虚，宁可用 README 全尺寸原图裁切。
4. **节奏匹配**：演示视频有自己的播放节奏，和旁白句点对不齐时要重剪或弃用——这比用静态截图 + GSAP 重演绎的确定性差很多（见 3.3）。
另外 harvest 进 catalog 时就按内容类型打过分，同类型重复素材（5 张意思相同的架构图）只留最佳一张。

### 3.3 滚动录屏改成全屏截图，不录视频

**教训**：用录屏（滚动网页的 captured video）当素材的坑：滚动速度和缓动不可控、运动中文字必然发虚、出现 seam、想改节奏就得重录。本期 s02 的做法是正确姿势：**只截一张完整长图（full-page screenshot），滚动在 HyperFrames 里用 GSAP 匀速重演绎**（65px/s + 切换停 1s）——逐帧清晰、seek 安全、可精确对齐字幕 cue，改速度只改一个常量。真正必须用视频的只有「动态过程本身」是内容的情况（如 ffmpeg-skill 官方 demo 视频），这时用**源 MP4**直接进时间轴，而不是拿播放器再录一遍屏——二次录屏把不可控从滚动扩大到了播放器的全部行为。

### 3.4 截屏和屏幕分辨率的关系、窗口大但内容只占一半（viewport ≠ 窗口）

截图分辨率**不取决于物理屏幕**，取决于 capture 时设置的 viewport 尺寸（CDP 里 window 大小 ≠ viewport：窗口含浏览器 chrome、viewport 是内容区；再叠加 devicePixelRatio，window 1000px 宽可能只截出 900px 内容）。「窗口开得很大但页面只用一半」的典型成因：页面自身 max-width 居中容器、响应式断点没命中、页面 zoom 不为 100%，或 capture 的是 window 而内容实际在更小的 viewport 里。**规则**：
1. capture 前显式设 viewport（如 1440×900 / 1920×1080），不要复用窗口默认值；
2. 长页面用 full-page（captureBeyondViewport）或分段截取再拼，别指望窗口滚动能截全；
3. 裁切以 **DOM 元素 bbox** 为准（measure 后裁），不要假设窗口尺寸=内容尺寸；
4. harvest 入库时顺手记录 viewport 设置和元素 bbox，下游 composition 裁切直接引用，避免二次猜。

### 3.5 SVG `<text>` 溢出为什么三轮都漏网（检测盲区确认）

确认这个判断，并补上完整的因果链：SVG `<text>` 没有 scroll/client 几何 → stock 检查器唯一沾边的 svg_text_overflow 规则要求 text 的父 `<g>` 恰好含 1 个 visible rect 才能配对 → 代码行的真实结构是「text + 行高亮矩形 + 行号」多子元素或单行高亮组（group bbox 只有首行高亮条约 32px 高），配对要么失败（漏检）要么 bbox 失真（假阳性）→ 三轮都是 stock 0 findings 放行、靠用户肉眼抓。补救已沉淀：**与其补检测，不如给文字真正有边界的容器**——代码/英文长行一律进 IDE/terminal 大面板（HTML 容器有 scroll/client，overflow 既可肉眼核又可被 panel_escape/html_clip 规则自动判），dense-layout-audit.py 作为第二道（8 采样点 + long_latin 启发式）。Phase 8 gate 从此双检。

### 3.6 避免 413：不要等出问题再拆，早拆 + 并行

本期的演化路径：整包派发 → 413 → 拆两批 → 又 413 → 去反引号 → 再拆三批（C1/C2/C3 并行，成功）→ 封面任务再次整包派发连续静默死亡（413 的空响应变体，连错误都不打）→ 最终模式「主会话预取素材 + 子会话单尺寸小批次」才稳定。**规则**：
1. **从第一次派发就按「会 413」的规格写指令**：一个子会话只干一个场景/一批同构任务；指令 ≤1KB、去掉反引号（zsh parse error 之源）、明确「只回复 done/路径清单」压报告长度。
2. **并行是默认而不是优化**：相互独立的批（不同场景、不同尺寸）从一开始就 `--no-session` 并行起，失败单批重派不影响其他批。本期 C1/C2/C3 三批并行全部一次成功，串行反而拖时长。
3. **图片是上下文炸弹**：一张 1920×1080 全帧吃掉大量 token，看 5 张全帧必死；要发图就先缩到 ≤640px 宽，或干脆主会话用代码判读代替子会话看图（本期选帧即改用坐标+代码判断，稳定通过）。
4. **验证中心化在主会话**：子会话不内嵌验证环节（那也是 413 诱因之一），文件落盘即自行验收（node --check / mtime / grep），子会话完成憋报告就 kill，产物为准。
5. **静默死亡 = 同义词**：子会话 exit 0 但零输出、零落盘时，按 413 处理直接走拆批路径，不要原样重试第三次。
