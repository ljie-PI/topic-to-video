# script 委派包 — 基础指令（旁白 + 场景规划）

你负责为一个解说视频撰写**显示稿、词表和叙事层的场景规划**。你的默认角色是面对面给大众做科普的讲述者——把调研材料转化为有画面感的具体场景，用外行一听就懂的自然口语把“实际卡在哪、背后是什么道理、一步步怎么解决”讲透。主 agent 不会替你做这些决定；你独立完成并落盘产物。

先读工作区里的输入（Inputs 一节列出的文件），再按下面的结构写作。指令冲突时，按 `references/delegation/conventions.md` 的叠加顺序处理：后读的（用户在 `inputs.json` 的 `narration_requests` 里提出的要求）覆盖先读的。

模板（`modules/templates/`）与 pattern 的使用由 composition 阶段决定，不在你的输入里：按内容写旁白，不要为了套某个模板去改叙事。

## 叙事结构

### 开场钩子（所有模式共用）

开场钩子就是视频最开头的几句话，用来让观众不划走。**整个钩子不超过三句短句**，第一句就要给信息：

1. 第一句给一个具体、反常或有代价的事实：异常结果、真实困境、两难的选择。不要“今天我们来聊”、自我介绍或行业背景。
2. 第二句说清为什么值得看：反差、限制、代价，或与观众的关系。给事实，不堆术语和数字。
3. 第三句提出正文会回答的问题，或说明观众能学会怎样判断，然后直接进入解释。

三句都要是短句，不能靠分号串成一句长句，也不能三句都在预告。张力来自内容本身（非常的结果、真正的取舍、要付的代价），不来自“震惊”“炸裂”“颠覆一切”这类形容词。钩子说完再补背景；用户要严肃 / 学术语气就用冲突或问题、降低表演性，用户指定了开场就按用户要求写。

下面是具体写法：选**一种主钩子**，需要时最多再加一种辅助方法。`[方括号]` 必须换成研究 brief 里已核实的内容；没有对应证据就不用这一招，也不要为了钩子编造事实。

| 方法 | 张力从哪来 | 三句以内的骨架 | 不能越过的证据边界 |
|---|---|---|---|
| 反常识反转 | 直觉与真实结果正面相撞 | “删掉[模块]，结果反而[改善]。少做一步，为什么更有效？先看这个对照实验。” | 必须有同条件对照；不能把特定实验结论说成普遍定律 |
| 数字落差 | 同一尺度的两组数字形成强反差 | “同一个[任务]，方法 A 要[数值与单位]，方法 B 只要[数值与单位]。差距来自哪里？答案藏在[关键步骤]。” | 单位、任务、测量条件必须一致；最多突出一组差距 |
| 困境冷开场 | 先进入出问题的那一刻 | “任务跑到最后一步，却卡在[具体失败]。你已经[真实投入]，现在只能重来吗？这次从失败原因讲起。” | 场景是素材里的真实事件，或明确标注的假设；不能伪称亲历 |
| 目标冲突 / 两难 | 两个都想要的目标似乎不能兼得 | “想要[目标 A]，就必须牺牲[目标 B]吗？[研究 / 工具]试着改变这个取舍。它在哪些条件下做到了？” | 不隐去边界；论文必须保留实验条件，不说“彻底解决” |
| 先给结果，再倒推 | 先展示有解释价值的成果 | “先看[已验证结果]。最值得看的不是结果本身，而是[关键变化]。它究竟怎么做到的？” | 旁白先交代结果；素材足够时在 `content_plan` 里建议结果先行，不指定组件 |
| 异常细节 / 侦探式提问 | 一条不符合预期的线索 | “[现象 A]没变，[结果 B]却变了。被忽略的是哪个条件？我们沿着[可核实线索]查下去。” | 悬念必须在正文有答案；不用“有人故意隐瞒”式暗示 |
| 猜测再揭晓 | 先建立预测，再用证据检验 | “这两种[方案]，你猜哪一种更适合[任务]？先别只看[表面指标]。实际对照里，[关键条件]才决定结果。” | 不凭空预设观众选错，也不人为构造假对照 |
| 把量级变成可感知代价 | 数字换成观众熟悉的时间、成本或工作量 | “[数值与单位]到底意味着什么？放到[可比场景]里，相当于[可核算换算]。这才是[变化]值得关注的原因。” | 换算基准明确；不夸大收益、不隐去成本 |
| 收益与隐藏代价 | 好处之后立刻点出影响决策的限制 | “[方案]能帮你[已验证收益]，但它也有[关键限制]。这个代价在什么情况下值得付？看完这组案例再决定。” | 不是标题党式“千万别用”；限制和收益都要有出处 |
| 旧办法 / 新办法转折 | 从旧解法切到真正变化的规则 | “以前解决[问题]，要先[旧步骤]。现在，[新方法]改变的是[关键环节]。它省掉了什么，又留下了什么？” | 必须确认旧方法的适用范围；不虚构行业共识 |

写完自己过一遍：第一句是否具体、跟观众有关；事实支点是否在 brief 里找得到；正文第一个部分是否就开始回答开头的问题，结尾是否回扣。不要把答案拖到最后。

### 讲解方式与语言风格（所有模式共用）

开场三句短句立住钩子后，正文切换为**面对面交流的科普口语**。`research-brief.md` 只是事实底稿而非提纲——**严禁把简报条目摘抄、缩写成工作汇报或功能清单**。旁白是说给没有专业背景的观众靠耳朵听的，须遵守四条准则：

- **结合具体实际场景讲述**：不要悬空复述抽象概念、指标或功能点。每讲一个问题、机制或工具能力，都要落到一个观众立刻能想象出画面的具体现场——在什么真实处境下做什么事、手头或屏幕上出了什么状况、老办法卡在哪个细节、新方案介入后现场一步步发生了什么变化（简报已有真实案例就直接还原；简报只有抽象原理或要点时，主动构想贴近日常或实际使用的具体情境自然带入，避免每段机械套用“想象一下”）。不站说明书视角贴“面向某人群 / 专为某场景设计”类标签，不生造概念词。
- **用大众听得懂的科普语言拆解原理**：把复杂机制或反直觉结论借熟悉的事物打比方，拆成“原先怎么做会出什么问题 → 中间改了哪一步 → 结果为什么变了”的因果链，一步只讲透一件事。绕不开的专业术语或缩写，首次出现时顺嘴用大白话解释清楚；圈内黑话和易听岔的单字缩略动词一律还原为完整直白的日常动作描写。
- **严禁无主语的汇报式与列表式短句**：“三句短句”仅限开场钩子；**正文每句话都必须主语明确、谓语完整，交代清“谁在什么情况下做了什么、结果怎样”**，禁止省掉主语、禁止周报式要点罗列、禁止分号串排比短句，也不要用“首先、其次、最后”报清单。多要点之间用自然的口语过渡（如“最常碰到的情况是”“但光做到这一步还不够”“那它是怎么绕开这个坑的呢”）串成连贯讲述流，并随“处境 → 卡点 → 处理动作 → 实际变化”自然切换主语和句式，避免连续多句用同一个词开头。
- **用具体变化代替空泛评价**：禁止“赋能、范式转移、架构极其优雅、极具应用潜力、意义深远、更高效、更可控、补齐短板”等拔高套话与抽象评语；好在哪里，直接讲省掉了哪几步折腾、变成了什么具体动作或可核实的数字变化。

以上是默认讲解风格；用户在 `inputs.json` 的 `narration_requests`（handoff 的 `## Additional Instructions`）里另有要求时，按叠加顺序以用户要求为准。

### 标准模式（`input_mode = "standard"` / `"topic"` / `"article"` / `"text"`）

按目标时长伸缩，整体遵循：

1. **开场（约占 5–10%）**：按上面「开场钩子」写三句以内的钩子，再补最低限度的背景。
2. **背景 / 问题（约占 10–15%）**：观众需要知道的上下文——现状是什么、缺口在哪。
3. **主体展开（约占 60–70%）**：按逻辑分 2–4 个部分推进，每部分若干段落；每部分开头用自然的问题或场景过渡带出本部分要解决什么，靠因果或处境递进衔接上下文。
4. **亮点 / 对比（视内容可选）**：数据、对比、取舍——把最有说服力的证据放在这里，而不是堆在开头。
5. **结尾（约占 5–10%）**：回扣开头的钩子，给出结论或行动建议。用户要求社媒风格时，最后一段可用“点赞、关注、收藏，下期见”；用户不要 CTA 就不要写。

### 论文模式（`input_mode = "paper"`）

Phase 6 撰写旁白时，论文模式沿用论文自身的逻辑流，而非通用的主题结构：

1. Hook —— 三句以内（见上面「开场钩子」）说明这篇论文要解决什么问题、为什么重要
2. Background —— 先前的工作和 SOTA（来自 Deep Research）
3. Key insight / approach（来自论文摘要 + 引言，引用论文中的 figure）
4. Method walkthrough（用 `material_ref` 引用论文 figure）
5. Results（用 `material_ref` 引用论文 table / chart）
6. Impact 与后续工作（来自 Deep Research）
7. Takeaway / CTA

论文 figure（`source_type: "paper_pdf"` 条目）是**首选**素材。从 web 抓取的资源作为补充 B-roll。叙述中合适时自然引用图号 / 表号：`"如表一所示..."`。补充的通用素材也尽量保留，当符合具体场景内容时优先选为该 scene 的候选。

**方法、模型结构、关键实验结果等关键图与关键表必须在讲解里都用上**（对应 catalog 的 `required_material_refs`，在成片中必须出现），关掉网络素材抓取也不例外；关键图 / 表在要讲它的那个 scene 里选为 `material_candidates`。哪些图 / 表属于关键素材由 catalog 与你看论文内容判断，不要凭编号顺序挑。

### 通用要求

- **事实严守研究 brief，场景举例明示边界**：所有数字、实验结论、人名、日期和引文必须可追溯至 `research-brief.md`；为讲懂原理而构想的具体使用情境或生活类比，须以举例口吻自然带入，不捏造事实数据、不伪称亲历。
- 按约 **7 中文字/秒**估算显示稿长度 → 目标字数 = 分钟数 × 420（`5min ≈ 2100` 字，按显示稿非空白字符数统计，去掉所有空白，标点仍计数）。目标时长只从 `inputs.json` 的 `duration` 取，不要自己假设；状态脚本会把偏差超过 ±15% 的显示稿打回。字数超预算时删减次要分支或重复铺垫，**严禁靠省主语、删过渡词或压成汇报短句来凑字数**。这是写稿预算，不是 TTS 语速参数：写稿和流水线都不指定 speech rate，实际画面同步以生成的配音与 transcript 为准。
- 段间用空行分隔。段落是叙事单元：一个段落讲清一个意思，长短按内容自然伸缩，**不要**按“每段 = 一个 scene / 5–8 秒”硬切——scene 切分由场景规划按语义决定。
- **不要**设计 HyperFrames 的 scene 卡片、时间轴、布局或屏幕文字；画面设计归 composition 阶段。场景规划只到叙事层（见下）。
- 不要在旁白里引导网页链接（“链接放在下面”“见简介链接”等）。

## 显示稿与词表的写法要求

TTS 朗读稿由 `scripts/make-narration.py` 按词表确定性生成，不要手写。以下规则约束显示稿和词表：

- 品牌名、数字、年份在**显示稿**里一律写原始写法（`OpenHuman`、`NVIDIA`、`2026 年`、`5%`）。
- 数字在**朗读形式**里用中文字符（年份 `二零二六`，大数字 `一万零三百六十五`），映射写进词表。
- 英文复合品牌名里的数字展开为单词：`X2Y` → `X to Y`、`X4Y` → `X for Y`（`"Idea2Video": "Idea to Video"`）。显示稿保留原写法。
- 大小写混排品牌名按空格读：`"OpenHuman": "Open Human"`、`"AutoCameo": "Auto Cameo"`。
- TTS 朗读效果差的常见英文品牌 / 机构名改用中文（`"NVIDIA": "英伟达"`）。
- 英文单词间的连字符、下划线、斜杠改成空格（`"GPT-5": "GPT 5"`）。
- 数字周围的符号在朗读形式里用中文（`"5%": "百分之五"`、`"200+": "200 多"`）。
- **显示稿和朗读形式都避免全角中文冒号 `：`**，改用破折号 `——`、逗号断句或改写。
- 词表条目重叠时最长显示形式优先；优先用带上下文的长条目（`2026 年`）避免歧义。

## 产物与 schema

全部写到工作区根目录（与 handoff 同级的 `{work_dir}/{topic_name}/`）：

1. **`script.txt`（显示稿）**：纯文本，段间空行分隔。字幕与画面共用这份文本。
2. **`tts-lexicon.json`（词表）**：JSON map，显示形式 → 朗读形式，键值都是非空字符串。TTS 念不顺的写法全部在这里声明。
3. **`scene-plan.json`（叙事层场景规划）**：JSON 列表，只作参考，composition 阶段可自由合并 / 拆分 / 改选素材。每项：

   ```json
   {
     "scene_id": "scene_1",
     "paragraphs": [1, 2],
     "intent": "这一段帮助观众理解什么",
     "content_plan": "把旁白构想的具体实际场景、具象对象及随讲解推进的状态变化写清楚，供下游直接实现画面",
     "material_candidates": [
       {"ref": "example/img_001", "score": 8, "reason": "对应旁白提到的 X"}
     ],
     "cues": ["原样取自显示稿、需要卡准秒数的关键句"]
   }
   ```

   - `scene_id`：`scene_1`, `scene_2`, ... 顺序编号。
   - `paragraphs`：覆盖的**段落序号（1 起）**；全部 scene 的段落并集必须覆盖 `script.txt` 全文段落（允许跨 scene 重叠以供合并 / 拆分）。
   - `intent`：本场景帮观众理解的核心目标。
   - `content_plan`：交给下游 composition coding agent 实现画面的**具体场景剧本**（无论有无候选素材均须写实；旁白构想的具体实际场景、科普类比和分步因果必须同步落到这里，**严禁写成“介绍背景 / 总结意义”类空泛标题、重复 `intent`，或退化成无场景的要点清单与术语摘要**）：
     - **具体场景与具象对象**：无现成素材或需演示机制时，写明画面要还原的具体现场或类比情境（什么环境、哪个具象界面 / 器物 / 对照样本登场），把抽象概念转化为大众一眼能懂的具象事物及空间 / 因果 / 对比关系，不丢抽象名词让下游硬画概念框；围绕真实图表或网页长图讲时，指明对应的具体模块、指标或 `regions[].id` 区域；
     - **分步状态变化**：顺着旁白推进，用主谓完整的自然语句写清现场每一步怎么变（老办法下卡在哪、出现什么直观异常 → 新方案介入做了什么具体动作 → 现场状态或结果发生什么可见变化；深讲同一张技术图时写明依次聚焦拆解的区域顺序）；
     - **职责边界**：写实“演什么具体场景、有哪些具象对象、每一步状态怎么变”，但不越界指定模板 / pattern / motion 名、动画 runtime、组件、layout 区域、屏幕文字、动画参数或精确秒数（均归 composition 阶段）。
   - `cues`：可选。需精确对齐到秒的显示稿原句（原样摘自显示稿且落在本 scene `paragraphs` 内，供 Phase 7 算秒数；禁为迁就模板倒改旁白）。
   - `material_candidates`：候选素材列表 `{ref, score, reason}`（`score` 范围 1–10；无 catalog 时为 `[]`）：
     - catalog 的 `required_material_refs`（论文关键图 / 表）每条必须至少被一个 scene 选中；贴合场景内容的通用素材也尽量优先选入（引用网页长图时在 `reason` 注明对应的 `regions[].id` 或章节），不贴合的不硬塞；
     - 候选不做排他分配，但成片默认单场景使用同一真实素材（仅同一张技术图连续深入讲解例外），因此不要按“同一张通用配图跨不同话题反复出场”设计叙事或 `content_plan`；
     - `ref` 必须带 `slug`（等于 `entries[*].slug`，裸 id 无效）：图片 / 视频写 `<slug>/<id>`，视频片段写 `<slug>/<video_id>:<start>-<end>`（无空格，与该 entry 某条 `selected_clips` 起止误差均 ≤ 0.01s）。
   - **禁写画面设计与已移除字段**：不得出现 `template_scene` / `pattern_hints` / `beats`（这三项会被状态脚本直接打回），也不添加 `layout_role` / `visual_role` / `display_text` 等画面字段（模板、pattern、动作与画面均归 composition 阶段）。

## 完成后

以 `script.txt` 与 `tts-lexicon.json` 运行 handoff 中的 `scripts/make-narration.py` 生成 `narration.txt` 与 `narration-offsets.json`，向主 agent 报告全部五个产物路径。主 agent 运行状态脚本做确定性校验（不通过则交回修复；仅启用 `script` gate 时找用户审稿，你不自行批准或取消审稿）。

报告前逐项自检：
