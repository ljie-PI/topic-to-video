# script 委派包 — 基础指令（旁白 + 场景规划）

你负责为一个解说视频撰写**显示稿、词表和叙事层的场景规划**。主 agent 不会替你做这些决定；你独立完成并落盘产物。

先读工作区里的输入（Inputs 一节列出的文件），再按下面的结构写作。指令冲突时，按 `references/delegation/conventions.md` 的叠加顺序处理：后读的（用户在 `inputs.json` 的 `narration_requests` 里提出的要求）覆盖先读的。

模板（`modules/templates/`）与 pattern 的使用由 composition 阶段决定，不在你的输入里：按内容写旁白，不要为了套某个模板去改叙事。

## 叙事结构

### 开场钩子（所有模式共用）

开场钩子就是视频最开头的几句话，用来让观众不划走。**整个钩子不超过三句短句**，第一句就要给信息：

1. 第一句给一个具体、反常或有代价的事实：异常结果、真实困境、两难的选择。不要“今天我们来聊”、自我介绍或行业背景。
2. 第二句说清为什么值得看：反差、限制、代价，或与观众的关系。给事实，不堆术语和数字。
3. 第三句提出正文会回答的问题，或说明观众能学会怎样判断，然后直接进入解释。

三句都要是短句，不能靠分号串成一句长句，也不能三句都在预告。张力来自内容本身（非常的结果、真正的取舍、要付的代价），不来自“震惊”“炸裂”“颠覆一切”这类形容词。钩子说完再补背景；用户要严肃 / 学术语气就用冲突或问题、降低表演性，用户指定了开场就按用户要求写。

下面是具体写法：选**一种主钩子**，需要时最多再加一种辅助方法。`[方括号]` 必须换成研究 brief 里已核实的内容；没有对应证据就不用这一招，也不要为了钩子编造事实。

| 方法 | 张力从哪来 | 三句以内的骨架 | 不能越过的证据边界 |
|---|---|---|---|
| 反常识反转 | 直觉与真实结果正面相撞 | “删掉[模块]，结果反而[改善]。少做一步，为什么更有效？先看这个对照实验。” | 必须有同条件对照；不能把特定实验结论说成普遍定律 |
| 数字落差 | 同一尺度的两组数字形成强反差 | “同一个[任务]，方法 A 要[数值与单位]，方法 B 只要[数值与单位]。差距来自哪里？答案藏在[关键步骤]。” | 单位、任务、测量条件必须一致；最多突出一组差距 |
| 困境冷开场 | 先进入出问题的那一刻 | “任务跑到最后一步，却卡在[具体失败]。你已经[真实投入]，现在只能重来吗？这次从失败原因讲起。” | 场景是素材里的真实事件，或明确标注的假设；不能伪称亲历 |
| 目标冲突 / 两难 | 两个都想要的目标似乎不能兼得 | “想要[目标 A]，就必须牺牲[目标 B]吗？[研究 / 工具]试着改变这个取舍。它在哪些条件下做到了？” | 不隐去边界；论文必须保留实验条件，不说“彻底解决” |
| 先给结果，再倒推 | 先展示有解释价值的成果 | “先看[已验证结果]。最值得看的不是结果本身，而是[关键变化]。它究竟怎么做到的？” | 旁白先交代结果；素材足够时在 `content_plan` 里建议结果先行，不指定组件 |
| 异常细节 / 侦探式提问 | 一条不符合预期的线索 | “[现象 A]没变，[结果 B]却变了。被忽略的是哪个条件？我们沿着[可核实线索]查下去。” | 悬念必须在正文有答案；不用“有人故意隐瞒”式暗示 |
| 猜测再揭晓 | 先建立预测，再用证据检验 | “这两种[方案]，你猜哪一种更适合[任务]？先别只看[表面指标]。实际对照里，[关键条件]才决定结果。” | 不凭空预设观众选错，也不人为构造假对照 |
| 把量级变成可感知代价 | 数字换成观众熟悉的时间、成本或工作量 | “[数值与单位]到底意味着什么？放到[可比场景]里，相当于[可核算换算]。这才是[变化]值得关注的原因。” | 换算基准明确；不夸大收益、不隐去成本 |
| 收益与隐藏代价 | 好处之后立刻点出影响决策的限制 | “[方案]能帮你[已验证收益]，但它也有[关键限制]。这个代价在什么情况下值得付？看完这组案例再决定。” | 不是标题党式“千万别用”；限制和收益都要有出处 |
| 旧办法 / 新办法转折 | 从旧解法切到真正变化的规则 | “以前解决[问题]，要先[旧步骤]。现在，[新方法]改变的是[关键环节]。它省掉了什么，又留下了什么？” | 必须确认旧方法的适用范围；不虚构行业共识 |

写完自己过一遍：第一句是否具体、跟观众有关；事实支点是否在 brief 里找得到；正文第一个部分是否就开始回答开头的问题，结尾是否回扣。不要把答案拖到最后。

### 标准模式（`input_mode = "standard"` / `topic` / `article` / `text"`）

按目标时长伸缩，整体遵循：

1. **开场（约占 5–10%）**：按上面「开场钩子」写三句以内的钩子，再补最低限度的背景。
2. **背景 / 问题（约占 10–15%）**：观众需要知道的上下文——现状是什么、缺口在哪。
3. **主体展开（约占 60–70%）**：按逻辑分 2–4 个部分推进，每部分若干段落；每个部分开头一句话交代这一部分要回答什么。并列点用清楚的层次（首先 / 其次 / 最后），因果关系写明因果。
4. **亮点 / 对比（视内容可选）**：数据、对比、取舍——把最有说服力的证据放在这里，而不是堆在开头。
5. **结尾（约占 5–10%）**：回扣开头的钩子，给出结论或行动建议。用户要求社媒风格时，最后一段可用“点赞、关注、收藏，下期见”；用户不要 CTA 就不要写。

### 论文模式（`input_mode = "paper"`）

Phase 6 撰写旁白时，论文模式沿用论文自身的逻辑流，而非通用的主题结构：

1. Hook —— 三句以内（见上面「开场钩子」）说明这篇论文要解决什么问题、为什么重要
2. Background —— 先前的工作和 SOTA（来自 Deep Research）
3. Key insight / approach（来自论文摘要 + 引言，引用论文中的 figure）
4. Method walkthrough（用 `material_ref` 引用论文 figure）
5. Results（用 `material_ref` 引用论文 table / chart）
6. Impact 与后续工作（来自 Deep Research）
7. Takeaway / CTA

论文 figure（`source_type: "paper_pdf"` 条目）是**首选**素材。从 web 抓取的资源作为补充 B-roll。叙述中合适时自然引用图号 / 表号：`"如表一所示..."`。

**方法、模型结构、关键实验结果等关键图必须在讲解里都用上**（对应 catalog 的 `required_material_refs`），关掉网络素材抓取也不例外；关键图在要讲它的那个 scene 里选为 `material_candidates`。哪些图属于关键图由 catalog 与你看论文内容判断，不要凭图号顺序挑。

### 通用要求

- 只使用**研究 brief 中的事实**——每个数字、人名、日期和引文都要可追溯。
- 按约 **7 字符/秒**估算显示稿长度 → 目标字数 = 分钟数 × 420（`5min ≈ 2100 chars`，按显示稿字数估算，去掉所有空白，标点仍计数）。目标时长只从 `inputs.json` 的 `duration` 取，不要自己假设；状态脚本会把偏差超过 ±15% 的显示稿打回。这是写稿预算，不是 TTS 语速参数：写稿和流水线都不指定 speech rate，实际画面同步以生成的配音与 transcript 为准。
- 段间用空行分隔。段落是叙事单元：一个段落讲清一个意思，长短按内容自然伸缩，**不要**按“每段 = 一个 scene / 5–8 秒”硬切——scene 切分由场景规划按语义决定。
- **不要**设计 HyperFrames 的 scene 卡片、时间轴、布局或屏幕文字；画面设计归 composition 阶段。场景规划只到叙事层（见下）。
- 不要在旁白里引导网页链接（“链接放在下面”“见简介链接”等）。

## 显示稿与词表的写法要求

TTS 朗读稿由 `scripts/make-narration.py` 按词表确定性生成，不要手写。以下规则约束显示稿和词表：

- 品牌名、数字、年份在**显示稿**里一律写原始写法（`OpenHuman`、`NVIDIA`、`2026 年`、`5%`）。
- 数字在**朗读形式**里用中文字符（年份 `二零二六`，大数字 `一万零三百六十五`），映射写进词表。
- 英文复合品牌名里的数字展开为单词：`X2Y` → `X to Y`、`X4Y` → `X for Y`（`"Idea2Video": "Idea to Video"`）。显示稿保留原写法。
- 大小写混排品牌名按空格读：`"OpenHuman": "Open Human"`、`"AutoCameo": "Auto Cameo"`。
- TTS 朗读效果差的常见英文品牌 / 机构名改用中文（`"NVIDIA": "英伟达"`）。
- 英文单词间的连字符、下划线、斜杠改成空格（`"GPT-5": "GPT 5"`）。
- 数字周围的符号在朗读形式里用中文（`"5%": "百分之五"`、`"200+": "200 多"`）。
- **显示稿和朗读形式都避免全角中文冒号 `：`**，改用破折号 `——`、逗号断句或改写。
- 词表条目重叠时最长显示形式优先；优先用带上下文的长条目（`2026 年`）避免歧义。

## 产物与 schema

全部写到工作区根目录（与 handoff 同级的 `{work_dir}/{topic_name}/`）：

1. **`script.txt`（显示稿）**：纯文本，段间空行分隔。字幕与画面共用这份文本。
2. **`tts-lexicon.json`（词表）**：JSON map，显示形式 → 朗读形式，键值都是非空字符串。TTS 念不顺的写法全部在这里声明。
3. **`scene-plan.json`（叙事层场景规划）**：JSON 列表，只作参考，composition 阶段可自由合并 / 拆分 / 改选素材。每项：

   ```json
   {
     "scene_id": "scene_1",
     "paragraphs": [1, 2],
     "intent": "这一段帮助观众理解什么",
     "content_plan": "用哪些内容、按什么顺序和方式讲，来达成 intent",
     "facts": ["数字、实体、列表、代码等关键事实"],
     "material_candidates": [
       {"ref": "example/img_001", "score": 8, "reason": "对应旁白提到的 X"}
     ],
     "cues": ["原样取自显示稿、需要卡准秒数的关键句"]
   }
   ```

   - `scene_id`：`scene_1`, `scene_2`, ... 顺序编号。
   - `paragraphs`：覆盖的**段落序号（1 起）**；所有 scene 的段落并集必须覆盖 `script.txt` 的全部段落，段落可以属于多个 scene（合并 / 拆分时）。
   - `intent`：这场景要帮观众理解什么。
   - `content_plan`：这场景讲什么、怎样展开。说清内容对象（哪组结果、哪个反例、哪张图）和展开顺序 / 演绎方式（先给结果再倒推、同条件对照、失败复盘、逐步推演、类比、图表解读）。不写模板 / pattern 名、组件、layout 区域、屏幕文字、动画参数或精确秒数——那是 composition 的设计空间；也不要把它写成 `intent` 的同义重复。
   - `cues`：可选。本 scene 里值得对齐到秒的关键句（例如要卡住画面切换的那一句），必须原样取自显示稿；Phase 7 用它们从配音里算出秒数。不要为了让某个模板好看而倒推旁白。
   - `facts`：这一段旁白依赖的关键事实（数字、实体、列表、代码）。
   - `material_candidates`：候选素材引用，每项含 `ref`、`score`（1–10）、`reason`。catalog 的 `required_material_refs` 必须至少各被一个 scene 选中（状态脚本会打回没覆盖的），但选为候选不等于已经出现在成片：实际画面由 composition 阶段落实。**只是候选，不做排他分配**；同一素材可以被多个 scene 候选。`ref` 的格式（即上面论文结构里说的 `material_ref`）：图片和视频用 `<slug>/<id>`，视频 clip 用 `<slug>/<video_id>:<start>-<end>`；`slug` 必须等于 catalog 的 `entries[*].slug`，id 只需存在于该 entry，裸 id 无效。即使两个 entry 都有 `img_001` 或同一个 video id，也必须用各自 slug 区分。clip 秒数与该 entry 的 `selected_clips` 对应——数字间不加空格，起止时间要与某一项相差不超过 0.01 秒。没有 catalog（`fetch_materials = false` 且不是论文模式）时留空列表。
   - **不包含** `template_scene` / `pattern_hints` / `beats` / `layout_role` / `visual_role` / `display_text`——模板、pattern、动作与画面都是 composition 阶段的设计空间；把场景计划写成那样会被状态脚本打回。

## 完成后

运行 `scripts/make-narration.py` 生成 `narration.txt` 与 `narration-offsets.json`（命令见 handoff 的 Outputs 一节），然后向主 agent 报告五个产物路径：`script.txt`、`tts-lexicon.json`、`scene-plan.json`、`narration.txt`、`narration-offsets.json`。主 agent 会运行状态脚本做确定性校验（字数 / 段落覆盖 / 素材引用），不通过就把原因交还给你修复；通过后默认自动继续，只有 `inputs.json` 的 `approval_gates` 包含 `script` 时才由主 agent 找用户确认。你不自行批准或决定取消审稿。

报告前自己先过一遍下面几项（状态脚本看不出来）：

- 每个事实、数字、人名、日期都能在 `research.md` 里找到；找不到的删掉或回报上游不足；写“据报道”也必须能给出出处。
- 开头三句内有具体的钩子：第一句就给出异常、困境或取舍，第二句说清为什么值得看，第三句承诺正文会回答的问题；后面才补背景。
- 各部分讲的是同一件事，段落之间没有断裂或重复；第一个主体部分就开始回答开头的问题。
- 每个 scene 的 `intent` 与它覆盖的段落对得上；`content_plan` 说清了用哪些内容和怎样展开，而不是把 `intent` 再说一遍；引用的素材能讲这段内容。
- 用户的要求（语气、结尾不要 CTA 等，见 `narration_requests`）都体现了。
- catalog 声明为 `required_material_refs` 的素材（论文模式的关键图 / 表）是否都被某个 scene 的 `material_candidates` 选中了。

任何一项不通过就自己改了再报告；如果问题是上游不足（简报缺证据、素材不对），在报告里写清楚是哪一项、建议回退到哪个阶段，不要自己编造补充。
